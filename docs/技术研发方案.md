# 技术研发方案 — 高情商回复助手（Android 单机版）

> 定位：单用户、侧载 APK、无账号/支付/后台。所有设计以「一个人能维护」为第一约束。
> 标记说明：**【P1】** = 第一期必须做，**【延后】** = 可延后，不做不影响主路径。

---

## 一、技术选型决策

### 1.1 移动端框架：原生 Kotlin + Compose vs Flutter

评分 1-5，分数越高越优（"系统能力适配成本"为反向指标，5 分表示成本最低）。

| 维度 | 权重 | 原生 Kotlin + Compose | Flutter | 说明 |
|---|---|---|---|---|
| 系统能力适配成本 | 45% | **5** | 2 | 本项目 70% 工作量在无障碍/悬浮窗/回填/OCR，全是系统 API |
| 开发速度 | 20% | 3 | 4 | Flutter 热重载与声明式 UI 更快出界面 |
| 学习成本（5=最低） | 20% | 2 | 3 | 你无 Android 原生经验；Dart 心智接近 Kotlin/Vue |
| 维护成本（5=最低） | 15% | 5 | 2 | 单栈 vs 双栈 + 插件版本地狱 |
| **加权总分** | | **4.05** | **2.70** | **结论：原生 Kotlin + Compose** |

关键论证（系统能力在 Flutter 下的真实代价）：

| 能力 | 原生实现 | Flutter 实现代价 |
|---|---|---|
| 无障碍遍历节点树 | 直接拿 `AccessibilityNodeInfo` 全量字段 | 必须走 Channel 序列化成 JSON；节点 refresh/performAction 还要回 native，读一次树 = 两次跨端往返 |
| 悬浮窗 | `WindowManager.addView` + 自定义 View | 需 PlatformView 把 `FlutterEngine` 附着到原生窗口，内存 +40~60MB，引擎崩溃会连带杀进程，社区插件多已停更 |
| 回填输入框 | 一次 `performAction` | 只能从 native 侧取 NodeInfo 发指令，往返多、失败原因难回传 |
| 截图/OCR | 直接 ImageReader、ML Kit 官方 SDK | 同样要桥，中文模型包配置常踩坑 |

结论：Flutter 省下的界面时间会在 4 个原生能力上成倍还回，还多背一套栈。**选原生。** 你的 Java/SpringBoot 经验对 Service/Intent/生命周期转移度很高，Compose 声明式 UI 与 Vue 心智相通；真正的学习成本在无障碍 API，而这部分换 Flutter 一样要学。

### 1.2 后端形态：客户端直连 vs 极简代理

| 维度 | 直连模型 API | Cloudflare Workers 代理 | 本机 FastAPI 代理 |
|---|---|---|---|
| Key 安全性 | 差（APK 可反编译提取） | 好 | 好 |
| 部署成本 | 0 | 免费额度足够 | 需电脑常开 + 内网穿透/域名 |
| 可用性 | 高（少一跳） | 依赖 CF 可用性，国内访问偶抖动 | 低（电脑关机即断） |
| 运维负担 | 无 | 管域名/证书/额度 | 需长期维护 |
| 自用场景必要性 | 够用 | 中等 | 低 |

**推荐：第一期直连，代码里预留 `LlmClient` 接口。** 单用户、APK 不外传，Key 风险主要是手机丢失 → Keystore 加密 + 厂商控制台设消费限额即可覆盖，代理层对自用工具是纯负债。**第二期【延后】**若想获得 prompt/话术库热更新能力再加 CF Workers，此时才有真收益。

### 1.3 数据库

**Room（SQLite 封装）**：编译期 SQL 校验、`Flow` 响应式查询、迁移可控，话术库检索与历史记录都靠它。键值类配置（Key、开关）走 `EncryptedSharedPreferences` + `DataStore`，不塞数据库。不引入任何服务端数据库。

## 二、整体架构

```
┌──────────────────────── 呈现层 ────────────────────────┐
│  主 App（Compose）: 生成页 / 历史 / 联系人 / 设置        │
│  悬浮窗（OverlayService）: 悬浮球 + 3 条候选卡片          │
└───────────────▲────────────────────────▲──────────────┘
                │ Flow                   │ 指令
┌───────────────┴──────────── 编排层 ─────┴──────────────┐
│  场景识别(包名+界面类型) → 上下文裁剪(最近6条/1500tok)   │
│  → 模板命中(优先) → Prompt 组装 → 单次流式请求(结构化 3 条)  │
└───────────────▲────────────────────────▲──────────────┘
                │                        │
┌──── 采集层 ───┴───────┐   ┌──── 模型层 ─┴─────────────┐
│ NodeTreeReader(无障碍) │   │ LlmClient(接口)            │
│ OcrCapture(ML Kit)     │   │ ├ DeepSeekClient (主力)    │
│ ShareReceiver(分享收图)│   │ ├ QwenClient   (备选)      │
│ ClipboardReader(手动)  │   │ └ GlmFlashClient(免费兜底) │
└───────────────┬────────┘   └───────────┬───────────────┘
                │                        │
┌───────────────┴──────── 存储层 ─────────┴──────────────┐
│ Room: contact_profile / conversation / generation       │
│       template / capture_rule                          │
│ SecurePrefs: api_key / model / overlay_enabled          │
└────────────────────────────────────────────────────────┘
```

核心链路（形态 A）：无障碍事件触发 → 提取可见消息 → 组装 prompt → **单次流式**请求（首条候选完整即渲染）→ 悬浮面板展示 → 点选 → `TextInjector` 回填（**永不自动发送**）。

## 三、关键技术路径

### 3.1 无障碍读屏（本项目最难的部分）【P1】

**Service 配置**：`eventTypes = TYPE_WINDOW_CONTENT_CHANGED | TYPE_VIEW_SCROLLED | TYPE_WINDOW_STATE_CHANGED`；`flags = flagReportViewIds | flagIncludeNotImportantViews | flagRetrieveInteractiveWindows`。全量监听太耗电，实际只在「悬浮球被点击」时按需读一次（事件只用于刷新缓存），这是省电关键。

**提取算法（通用启发式，不硬编码任何 App）**：

1. **前置判定**：`root.packageName` 不在白名单（微信/BOSS/钉钉/飞书）直接返回。当前前台包用 `AccessibilityWindowInfo` 或 `UsageStatsManager` 交叉确认。
2. **定位输入框锚点**：DFS 遍历，候选条件 `isEditable == true` 或 `className == "android.widget.EditText"`，且 `isVisibleToUser`，取 **bounds 面积最大** 的一个。
3. **定位消息容器**：从输入框向上回溯 2~4 层父节点（`input.parent.parent.parent`），选第一个「子节点数 ≥ 2 且 bounds 高度 > 屏幕 30%」的祖先。找不到就退化为「屏幕 y < 输入框 y 的所有可见叶子节点」。
4. **收集叶子**：遍历容器子树，取 `text` 或 `contentDescription` 非空、长度 ∈ [1,200]、非输入框自身、`bounds` 完全在屏幕内（`isVisibleToUser`）的节点。
5. **排序**：按 `bounds.top` 升序即阅读顺序。
6. **避历史消息**：只取「当前屏幕可见」的节点，天然排除已滚出屏幕的历史；再叠加 `sessionFingerprint = hash(顶部对方昵称 text + 输入框 bounds)`，指纹变化即视为切换会话、清空缓存。
7. **区分"对方说"vs"我说"**：用**双信号投票**，不依赖颜色（深色模式不可靠）：
   - 主信号：`node.bounds.centerX()` 相对容器宽度的位置，右侧 1/3 = 我，左侧 1/3 = 对方；
   - 辅信号：节点左邻/右邻 40dp 内是否有 `ImageView`（头像）——头像在左=对方，在右=我；
   - 两信号冲突或居中时标记 `UNKNOWN`，悬浮窗给出「↓对方 / ↓我」切换按钮由用户一键修正（比猜准更划算）。

**App 差异处理**：不写 `resource-id` 硬编码。第一次在某 App 跑通后，把「输入框 viewId（若存在）+ 容器相对深度」写入 `capture_rule`，后续优先命中，形成**每 App 自学习**。若节点树为空（WebView/自绘版本），2 秒超时直接提示「当前界面无法读取，请用截图/粘贴」，**绝不无限重试**。

### 3.2 回填输入框【P1】

```kotlin
val args = Bundle().apply {
    putCharSequence(AccessibilityNodeInfo.ACTION_ARGUMENT_SET_TEXT_CHARSEQUENCE, text)
}
val ok = node.performAction(AccessibilityNodeInfo.ACTION_SET_TEXT, args)
```

要点：节点必须先 `refresh()` 保证未失效；`isEditable` 为 true 才可靠；微信需保证输入框已获得焦点（先 `ACTION_FOCUS` 再 `ACTION_SET_TEXT`）。

三级降级链（`TextInjector` 里串成责任链，逐级 try）：

| 级别 | 手段 | 适用 |
|---|---|---|
| L1 | `ACTION_SET_TEXT` | 绝大多数原生 EditText |
| L2 | 写剪贴板 + `ACTION_FOCUS` + `ACTION_PASTE` | WebView 内输入框（部分飞书/BOSS 版本） |
| L3 | 写剪贴板 + 悬浮窗提示「已复制，长按粘贴」 | 全部失败时兜底，永不空手 |

### 3.3 悬浮窗【P1】

- **权限**：`Settings.canDrawOverlays()` 判定 → 跳 `ACTION_MANAGE_OVERLAY_PERMISSION`。必须和「开启无障碍」放在同一个引导页，否则用户会卡在这两步之间。
- **前台服务**：Android 14 强制 `foregroundServiceType="specialUse"` + 声明 `PROPERTY_SPECIAL_USE_FGS_SUBTYPE`；通知 channel 用 `IMPORTANCE_LOW`，文案「监听中 · 点击暂停」。
- **参数**：`TYPE_APPLICATION_OVERLAY` + `FLAG_NOT_FOCUSABLE`（**关键：不抢焦点、不弹输入法、不打断打字**）；仅当悬浮窗内有 EditText 时才临时移除该 flag。
- **拖拽**：`setOnTouchListener` 记 `rawX/rawY` 与 `params.x/y`，`ACTION_MOVE` 时 `updateViewLayout`；位移 < 8dp 判为点击。
- **不遮挡输入框**：用 3.1 的输入框 `bounds.top`，把悬浮条放在 `inputTop - height - 8dp`；键盘弹起时监听 `TYPE_WINDOW_STATE_CHANGED` 重算；支持贴边收起成 24dp 圆点。

### 3.4 截图 OCR（形态 B）【P1 部分 / 部分延后】

| 路径 | 授权 | 结论 |
|---|---|---|
| 系统分享入口（`ACTION_SEND` 收图） | 零权限、用户主动 | **【P1】** 成本最低、最稳 |
| Photo Picker 手动选图 | 零权限 | **【P1】** |
| `AccessibilityService.takeScreenshot()`（API 30+） | 零弹窗 | **【延后】** 做成第二期一键截屏 |
| MediaProjection | 每次会话授权弹窗 + 常驻录屏通知 | **不做**，体验差 |

**OCR 引擎：ML Kit `text-recognition-chinese`（本地、免费、离线，模型按需下载约 20MB）**。缺点明确：中文标点常丢、竖排不支持、手写体差。应对是**不修 OCR**——OCR 只取文字，标点补全交给模型（prompt 注明「原文可能缺标点」），角色判定交给用户点选。云端 OCR（腾讯/百度）准确率更高但引入 Key 与费用，自用不值。

### 3.5 上下文与成本控制【P1】

| 措施 | 参数 |
|---|---|
| 采集 vs 送模型 | 采集层取屏幕内可见消息（上限 20 条，符合 F-01）；编排层只把最近 6 条送模型 |
| 单条消息截断 | 200 字 |
| Prompt 输入上限 | 1500 token，超了从最旧消息开始丢 |
| 模板优先 | 本地话术库按（关系×目标×关键词）命中 → 直接返回 3 条，**不调模型**，覆盖约 30% 请求 |
| 结果复用 | `hash(消息+目标+风格)` 相同且 30 分钟内 → 直接复用 |
| 模型侧缓存 | DeepSeek 自动磁盘缓存，命中部分按 1/10 计价 |

## 四、数据模型（Room）

| 表 | 字段 | 说明 |
|---|---|---|
| `contact_profile` | id, name, alias, relation_type(领导/同事/客户/朋友/家人/暧昧/陌生), tone_pref(正式/轻松/亲密), taboo(JSON 数组), notes, created_at, updated_at | 关系决定语气，taboo 进 prompt 作负向约束 |

| `app_config` | key(PK), value(JSON) | 非敏感配置；api_key 单独走 SecurePrefs |

索引：`conversation(app_pkg, captured_at)`、`generation(created_at)`、`template(relation_type, goal_type)`。

## 五、模型选型与成本

| 候选 | 输入价（元/百万 tok） | 输出价 | 定位 |
|---|---|---|---|
| DeepSeek-V3.2（`deepseek-chat`） | 2（缓存命中 0.2） | 3 | **主力生成**，中文口语感最好 |
| 通义 `qwen-plus` | 0.8 | 2 | **主力备选**，长上下文更宽容 |
| 智谱 `GLM-4-Flash` | 免费 | 免费 | 场景分类、解释理由、断网兜底的快速改写 |

成本估算（每天 20 次，每次输入 1200 tok / 输出 400 tok）：
- DeepSeek：20 ×(1200×2 + 400×3)/10⁶ = **¥0.072/天 ≈ ¥2.2/月**
- qwen-plus：20 ×(1200×0.8 + 400×2)/10⁶ ≈ **¥1.1/月**

结论：**月成本 < ¥5，可忽略**。因此选型权重应放在「回复质量」而非单价 → 主力 DeepSeek，分类/解释用免费 Flash。三家都提供 OpenAI 兼容接口，`LlmClient` 用一个 OkHttp + SSE 实现即可全兼容，切换只改 baseUrl 与 model 名。

## 七、里程碑计划

| 阶段 | 周期 | 交付物 | 验收标准 |
|---|---|---|---|
| **M1 闭环验证**【P1】 | 1-2 周 | Compose 单页（粘贴框+关系/目标选择+3 卡片+复制）、`LlmClient`(SSE)、SecurePrefs 存 Key | 真机侧载，粘贴一段微信对话，10 秒出 3 条，点卡片复制成功 |
| **M2 主路径打通**【P1】 | 2-3 周 | 无障碍服务 + 输入框锚点 + 可见消息提取 + 悬浮球 + `TextInjector` 三级降级 | 微信页点悬浮球 → 自动读最近 3 轮 → 出 3 条 → 点一条进输入框 |
| **M3 多 App + 兜底**【P1】 | 2 周 | BOSS/钉钉/飞书适配 + `capture_rule` 自学习 + 分享入口 + Photo Picker + ML Kit OCR + 预置 100 条话术库 | 4 个 App 各连跑 3 次成功；OCR 路径能出结果 |
| **M4 打磨**【P1/延后】 | 1-2 周 | 联系人档案、历史、收藏、无障碍心跳自检、OEM 引导页、prompt 裁剪与结果复用 | 连续 7 天无崩溃；无障碍被杀 15 分钟内提醒 |

M1 是硬性顺序要求：先把「文本 → 模型 → 3 条 → 复制」这条最确定的链路跑通，再叠加系统能力，避免一开始就死在无障碍调试上。

## 八、技术风险与遗留债务

| # | 风险 | 触发条件 | 应对 |
|---|---|---|---|
| 1 | 无障碍服务被杀 | 息屏、内存回收、MIUI 优化 | 前台服务保活 + `getEnabledAccessibilityServiceList()` 心跳（WorkManager 15min + 回前台校验）+ 通知栏一键跳设置 + 降级到通知栏入口 |
| 2 | 微信节点结构变更 | 微信大版本改版/自绘化 | 不硬编码 resourceId，只用「可编辑 + 面积 + 位置」三要素；读树为空 2 秒超时切 OCR；手动粘贴永久兜底 |
| 3 | OCR 中文标点丢失、分不清角色 | 截图只有气泡无角色 | OCR 只取文字不判角色（用户点选「这段是对方说的」）；标点交模型补全，不写自研纠错正则 |
| 4 | 模型 Key 泄露 | APK 被他人拿到 | Keystore 加密、设置页不明文回显、控制台月限额、预留代理切换 |
| 5 | 悬浮窗与输入法冲突 | 键盘弹起、全屏输入 | `FLAG_NOT_FOCUSABLE` 不抢焦点；按输入框 bounds 定位到其上方；贴边收起；监听窗口变化重算 |
| 6 | `ACTION_SET_TEXT` 在部分 App 无效 | WebView 输入框 | L1→L2→L3 降级，失败 App 记入 `capture_rule.ok_count`，后续直接走 L2 |
| 7 | 厂商后台管控导致重启 | 各家省电策略 | 首启 OEM 引导页逐项跳转；不追求 100% 保活，靠「缺失即提示」而非硬抗 |

**遗留债务（明确接受）**：不做 MediaProjection 常驻录屏；不做多设备同步；不做离线小模型；`capture_rule` 不做云端共享。

```
└── core/                # Result, TokenCounter, PromptBuilder, Logger, PermissionGate
```

模块边界：`ui → domain → data`，`service/capture/inject` 只依赖 `domain`，禁止反向依赖，禁止 `ui` 直接调 `data`。

### 第一期 vs 延后 一览

- **【P1】** 原生 Kotlin+Compose、直连模型、Room、无障碍读屏、ACTION_SET_TEXT+降级、悬浮窗、分享/选图 OCR、模板优先、5 张核心表、M1~M3
- **【延后】** CF Workers 代理、MediaProjection、`takeScreenshot` 一键截屏、云端 OCR、多模型自动路由、`capture_rule` 云端共享、语音输入、消息自动回复（不做自动发送，只做回填）

## 十、与 PRD 对齐的增量修订（V1.2 · 已锁定）

> 本章优先级高于前九章冲突表述；已与 PRD 定稿一致，无开放问题。

**生成方式**：单次流式请求（非 3 并发），输出固定 JSON（3 个 `{text, why}`），`stream=true` 增量解析，第 1 条收齐即渲染。理由：F-06 要求一次返回 3 条、F-07 要求解释互不复用，3 并发成本 ×3 且风格趋同。

**结构兜底（不可退）**：解析失败重试 1 次（temp −0.3）；仍失败走本地话术库 3 条 + 通用解释，**卡片必须打「离线模板 · 未调用模型」角标（中性灰，非警告色）与来源说明**，不得让用户误认为模型生成。解析层硬断言「3 条齐全 + `why` 非空 + 3 句互不相同」，**四条畸形返回**——只回 2 条 / 3 句解释同一句 / 解释为空 / 某条 `text` 为空——均须整批降级并打角标；**空串与纯空格一律视为无效**（`text` 与 `why` 同判，校验前先 `trim()`）。

**降级时必须说人话（对应 PRD A4）**：用户刚看到文字在流式打出来、整批却变成模板，若不给解释等同于"内容凭空消失"。故整批降级时结果区顶部固定展示一句「这次没生成成功，给你 3 条备用说法」，**是页面内文案而非弹窗**；超时走另一分支（保留进度态文本 + 「重试」按钮），Key 错走第三分支（跳设置并高亮字段）。**三个分支互斥，判定优先级 Key > 超时 > 解析**（PRD 表格中的书写顺序只是枚举顺序，不是优先级，联调与验收均以本条为准）。

**性能**：固定 prompt 前缀吃厂商缓存 + 关思维链 + `max_tokens≈600` + 只发 6 条 + 连接池/DNS 预解析，保首字 2.5s、全量 6s。**2.5s「首字」口径 = 第一个可见字符出现在进度态**（仅骨架屏转圈判不达标）；卡片可点受 6s 约束，不做逐条可点（会引入"点完被整批回滚"的竞争）。悬浮面板 **XML 预 inflate 并在 OverlayService 启动时 attach（GONE），点击只切 visible**；300ms 为硬线，**不接受冷启动首次例外**（预热在服务启动完成）。

**枚举与表**：关系 7 值 / 目标 6 值 / 风格 3 值（稳/暖/机灵）；`generation` 增 `style`、`adopted_candidate_index`、`source(model|offline_template)`。新增 `usage_event(id, type, ts, app_pkg, latency_ms, sim_score, is_adopted, relation_enum, goal_enum, style_enum)`，纯本地、仅设置页展示；**三个枚举是为了定位"哪个场景在失败"（指导改 prompt），不是给自己打分**。硬约束：**不存原文、不存候选文本、不存联系人名**，只存枚举与标量——否则第七章隐私承诺被自己的埋点破功。

**整批原子性（不可退）**：一次生成的结果要么全部来自模型、要么全部来自离线模板，**不允许 3 条里 2 条模型 1 条模板**。实现上解析层做全量校验后才 emit 整批：任一条不满足断言 → 整批判失败 → 走模板兜底，`source` 只有两个取值。UI 因此只需读一个字段决定角标，不存在"部分兜底"的表达。

**模型设置（F-13）**：`baseUrl / apiKey / modelName` 三项可填 + 「连通性自检」（8 token ping，回显耗时与错误码），预置三家快捷模板；Key 存 EncryptedSharedPreferences。

**A→B 降级**：读屏返空不跳首页，生成页原地进「已降级态」：横幅「没读到内容」+「改用截图」「改用粘贴」，已选关系/目标/风格保留；无障碍未开启则悬浮球置灰 + 横幅跳设置。

**回填失败（不可退）**：L2 失败即**强制写剪贴板 + Toast「已复制，请长按粘贴」**，不抛异常、不弹错误框、不锁 UI；不接受「加个弹窗更友好」的改动。

**页面**：7 页与 3 Tab 按 PRD；包 `ui/home, generate, ocr, overlay, history, settings, contact`。

**隐私与存储**：原文不出机，上行仅 prompt 文本片段；生成页提供「查看将要发送的内容」；`conversation.expire_at` + WorkManager 每日清理 >7 天；库 >50MB 从最旧删起；**零第三方 SDK**。

**F-01 读屏（PRD 已按本方案修正）**：读**当前屏幕可见**消息（通常 8–12，上限 20），**不滑动不滚屏**，送模型仅 6 条；验收含「全程无界面跳动、不触发已读」。实现约束：`MessageExtractor` **禁止调用任何 `ACTION_SCROLL_*`**，20 只是数组防御上界，够不到就按实际条数走，降级判断看「是否有对方最后一句」而非条数。

## 十一、V1.3 增量修订（已锁定 · 2026-11-12）

> 本章优先级高于前九章冲突表述。新增「模式」维度、表情档位、朋友圈文案、润色、画像演化。

### 11.1 管线抽象：一条管线三个出口

```
输入(text | image) → task_type ∈ {reply, post, polish}
  → 约束  reply: relation × goal
         post : scene × length
         polish: tone
  → 共用 style{稳/暖/机灵} + emoji{none/light/rich}
  → 单次流式 → 3 × {text, why} + source{model|template}
  → 出口  复制(全部) / 回填(仅 reply)
```

**实现要点**：`GenerateReply` 只认 `GenRequest(taskType, input, constraints, style, emojiPolicy)`；prompt 模板按 `taskType` 查表，其余（流式、整批校验、降级、表情后处理）完全复用。新增一种说话场景 = 加一个枚举 + 一个模板文件，不改管线。

### 11.2 表情后处理（必须做，不能只靠 prompt）

模型一定会滥用 emoji。`EmojiFilter.apply(text, policy)`：
- `none`：按码点剥离（0x1F000–0x1FAFF、0x2600–0x27BF、U+FE0F、U+200D，以及 `Character.getType == OTHER_SYMBOL`），并清掉残留的双空格与句首空格；
- `light`：保留 1 个，其余剥离；
- `rich`：保留 ≤3 个，且不放在句首。

**顺序**：解析整批通过 → 对 3 条 `text` 各自过滤 → 再判「3 句 why 互不相同」与「3 条差异 ≥60%」（**过滤后**计算，emoji 不参与差异）。模板兜底的 3 条同样过滤。

### 11.3 朋友圈（post）与 Vision

- 输入图：`PhotoPicker` 选 1 张（零权限），长边压到 1024、JPEG 80；
- 先让**视觉模型输出 1~2 句画面描述**，把描述拼进 prompt，不让正文模型反复看图（省 token、结果更稳）；
- 多图只取第一张，其余丢弃并在 UI 写明；
- 图**不落盘、不入库、不进备份**，OCR/生成完成即释放；
- 首次使用带图路径时弹一次明确说明：此图将发送给模型厂商；设置页可关「允许上传图片」，关掉后降级为纯文字发圈。

**模型侧**：`deepseek-flash` 支持图片输入（需实测确认），`LlmClient` 的 message content 需支持 `[{type:"text"},{type:"image_url"}]` 数组形态；不支持时按 `qwen3.x` 视觉模型兜底。

### 11.4 润色（polish）

- 强约束写进 system prompt：**不改事实、不新增信息、不加承诺/时间**；
- `why` 语义变化：不再是「为什么这样说」，而是「**改了什么**」（把哪句换成了哪句，攻击性/长度/主动性如何变）；
- 两个入口共用同一状态机：独立模式 = 首页直达并切到 `POLISH`；折叠条 = 生成页内 `ModalBottomSheet`，**不挤压候选列表**；
- 验收：对输出做一次「事实点回溯」检查（人眼或脚本），任何原文没有的具体承诺即判缺陷。

### 11.5 画像演化（Profile Evolution）

**数据流**（全本机）：

```
采纳事件(usage_event.is_adopted=1, 已存枚举+相似度)
  → 攒够 3 条 或 距上次 ≥7 天
  → WorkManager 异步提炼（Constraint: 联网 + 电量不低）
  → 输入只含「被采纳的候选文本 + 用户手改后的最终文本」
  → 输出 1 条画像变更提案 {field, newValue, evidenceTs}
  → 写入 profile_change 表（可撤销）
  → 结果页轻提示条 + 撤销
```

**硬约束**：一次只改 1 条；每次变更必须带 `evidenceTs` 指向具体某次生成；`profile` 表只存 4 条摘要 + 时间戳，**不存原话**；提炼失败静默重试，不弹窗；`auto_evolve` 关闭后退化为静态手动档。

### 11.6 数据模型增补

| 表 | 变更 |
|---|---|
| `generation` | + `task_type`, `emoji_policy`, `scene_enum`, `tone_enum` |
| `usage_event` | + `task_type`（采纳率按类型分算，避免被发圈稀释） |
| `contact_profile` | + `auto_evolve(0/1)`, `summary_json`（4 条画像）, `evolved_at` |
| **新增** `profile_change` | id, contact_id, field, old_value, new_value, evidence_generation_id, ts, reverted(0/1) |

### 11.7 验收增补

1. 切模式后已填原文不丢，且选择器随之切换；
2. `emoji=none` 三次生成，3 条候选 emoji 计数均为 0；
3. 同输入切 `none→rich`，**仅 emoji 变化**时不得判定为"候选差异达标"；
4. 发圈结果页不存在回填按钮；
5. 润色输出中出现的每个承诺/时间，必须能在输入原文找到；
6. 画像每次变更都能在结果页看到并可撤销，24h 内不出现第二次同字段变更。
